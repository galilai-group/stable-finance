# Experiments

Reproducible studies built on stable-finance. Nothing here is part of the
package; the library never imports it. `experiments` is a package of its own:
run its scripts from the repository root with `python -m experiments.<script>`.

Results are not committed. Everything under `results/` is regenerated by the
pipeline below, and every rerun gives the same rows.

```bash
uv sync --extra hf --extra mds --extra experiments
export STABLE_FINANCE_CACHE=/path/with/space      # downloads and caches live here
```

## Pipeline

| Step | Script | Output |
|---|---|---|
| 1. Cache months | `python -m experiments.month_cache 2020-07 2020-08` | `$STABLE_FINANCE_CACHE/experiments/market1t-YYYY-MM.npz`, about 120 MB a month |
| 1b. Cache months, v2 (optional) | `python -m experiments.months` | `$STABLE_FINANCE_CACHE/experiments/market1t-v2-YYYY-MM.npz`, about 200 MB a month, every month of the store |
| 2. Real forecasts | `python -m experiments.signals` | `results/signals/{reversal_15m,ridge,lasso}.npz`, `ic_table.json` |
| 3. Run a spec | `python -m experiments.run experiments/specs/<spec>.json --workers 4` | `results/<name>/rows.parquet`, `manifest.json`, `series.npz` |
| 4. Learned policy | `python -m experiments.policy` | `results/policy/policy.json` |
| 5. Stage costs | `python -m experiments.bench` (on an idle machine) | `results/bench/bench.json` |
| 6. Figures | `python -m experiments.figures` | `results/figures/*-{light,dark}.png` |
| 7. Solver convergence | `python -m experiments.mv_solver --efq 0.7 1.0 0.0 --variants 200` | `results/mv_solver/summary.json`, `per_decision.npz`: the mean-variance book under the default 400-iteration FISTA and solved to convergence (`mv_solver="restart"`), with iterations, optimality residuals, distance from a verified exact optimum, seconds and the change in scores |
| 8. Inference | `python -m experiments.inference <run>` (needs `arch`, in the extra) | `results/<run>/inference.parquet`, `inference.json`: Lo-adjusted and HAC Sharpe per row; model confidence set, SPA, StepM, deflated Sharpe (effective trials) and PBO per group |
| 9. Sanity checks | `python -m experiments.sanity [--results DIR] [--quick]` | `results/sanity/report.json`: analytic TCs, fundamental law, placebo, IC-1 invariance, look-ahead canaries, cost identity, latency, determinism -- PASS/FLAG/WARN/FAIL/SKIP |
| 10. Risk models | `python -m experiments.risk_eval` | `results/risk_eval/risk_eval.json`: each risk model scored out of sample (GMV variance, Diebold-Mariano, bias by half hour) |
| 11. Dynamic trading | `python -m experiments.dynamic` | `results/dynamic/dynamic.json`: aim portfolio, partial adjustment and no-trade bands tuned on July, scored on August |
| 12. Walk-forward signals | `python -m experiments.signals_wf [--window N] [--ofi]` | `results/signals_wf/{ridge_wf,lasso_wf}.npz`, `ic_table.json`: daily refits with purged, embargoed CV |
| 13. More figures, appendix | `python -m experiments.figures_v2`, `python -m experiments.appendix` | fundamental-law, daily-CI, seed, break-even, walk-forward and MCS figures; `appendix/appendix.csv` (every row) and `lookup.csv` (IC to break even) |

Run each with `uv run --extra experiments python -m ...`. `month_cache` streams the
Hugging Face day store one day at a time and deletes each unpacked day after
reading it, so a month needs about 1.6 GB of download plus one unpacked day
(about 0.6 GB) of scratch space.

## Month cache v2 and every month of the store

`month_cache_v2` reads the same days in the same pass and writes
`market1t-v2-YYYY-MM.npz` (about 200 MB a month): every v1 array, bit for bit
the same as the cached v1 files, plus what cost realism and order flow need:

| Array | What |
|---|---|
| `realized_mid` | midquote-to-midquote forward returns at the store's horizons, from the decision row, NaN on the same structural cells as the VWAP label |
| `exec_{bid,ask}_price_{1,5,30}s` | the touch 1, 5 and 30 seconds after the decision (5 s is v1's `exec_` pair) |
| `dollar_volume`, `day_close` | the name's dollar volume and last midpoint over its whole day, on every decision row of that day (not causal within the day) |
| `ofi_features` (`ofi_60s`, `ofi_300s`) | best-level order-flow imbalance (Cont, Kukanov and Stoikov 2014) over the last 60 and 300 seconds, divided by the average depth |

```bash
python -m experiments.month_cache_v2 --days 2020-08-12 --check   # one day, checked against v1
python -m experiments.months --list                              # the store's months and their state
python -m experiments.months --keep-raw 2020-07 2020-08          # build every month, in order
```

`months` builds each month in date order and deletes its download and per-day
files once its cache is written, so peak disk is one month's download plus one
unpacked day (about 2.5 GB) plus the finished caches. It is safe to kill and
rerun: done months are skipped, days and months are written atomically, a lock
file stops a second copy, and progress goes to `months.log` beside the caches.
`--v1` also writes each month's v1 file, cut from the v2 one.

A spec opts in with three keys; a spec without them runs exactly as before
(same task keys, rows and row ids):

| Key | Options | Default |
|---|---|---|
| `cache` | `"v1"`, `"v2"`; v2 adds an `adv` market column, the mean daily dollar volume over the `adv_days` (default 20) days strictly before each decision's day, history month included | `"v1"` |
| `returns` | `"vwap"` (the store's), `"mid"` (v2's midquote returns, for the risk history too; same universe either way) | `"vwap"` |
| `latency` | `0` (the decision's quote), `1`, `5`, `30` seconds to the touch an order meets; 1 and 30 need v2 | `5` |

`returns` and `latency` may be lists: each combination becomes a task axis, and
rows carry the keys the spec names.

## Specs

| Spec | Question |
|---|---|
| `e1_transfer_map` | How does a forecast's IC become gross and net Sharpe? Six ICs × three noise placements × three horizons × five constructions × whole cross-section or deciles × three EFQs × overlapping or held scoring |
| `e1b_mean_variance` | The same for the cost-aware mean-variance allocator, whose book depends on the cost it is billed |
| `e2_where_errors_sit` | At equal IC and equal per-decision IC dispersion, does it matter whether the errors sit in the tails, the middle or at random? |
| `e3_horizon_overlap` | How much do overlapping forward returns inflate the booked P&L at each horizon, and how much less do persistent (by-name) errors trade? Uses `copula_forecast` at half-lives of none, 3 and 12 decisions |
| `e4_harness_sensitivity` | For a fixed forecast, how far do the risk model, neutralization, Grinold scaling and the liquidity screen move net Sharpe? |
| `e5_real_signals` | Where do cheap real forecasts land on the oracle's map? |
| `e6_sanity_checks` | Do the controls behave? IC-0 placebos under ten seeds must centre on zero, the seed-to-seed spread at IC 0.03 says how much one draw can mislead, and at IC 1 the three oracles must coincide |
| `e1x_expected_ic` | E1 with expected-IC oracles (scatter "sampling", three seeds) at 15 minutes: the version whose gross Sharpe can be read against the fundamental law |
| `e7_factor_oracle` | Do beta neutralization and a factor risk model help when forecast errors are factor bets (`factor_forecast`, 0/30/60% factor share)? |
| `e8_costs` | Cost realism on cache v2: midquote vs VWAP returns, 1/5/30 s latency, 2020 fees, for an oracle and the real reversal signal |
| `e9_impact_capacity` | Capacity: the impact model at $0.1M-$100M against the cross-spread model (cache v2 supplies `adv`) |
| `e10_mv_converged` | E1b with the converged mean-variance solver (`mv_solver="restart"`): the solver error in the published mean-variance results |

A spec names the evaluation month, the risk-history month, the horizons, the
forecasts and a grid of `BacktestConfig` settings. `"rebalance": "horizon"`
holds each book for the forecast horizon and books its return once; at a
horizon no longer than `decision_spacing` (default 300 s) it is the same as
`"every_decision"` and runs once under that name. `exclude` drops
combinations. Every rerun is byte-identical: oracle seeds are in the spec,
rows are written in task order, and the manifest records the commit, the spec
and a hash of every input array. Each (forecast, horizon) task is
checkpointed under `results/<name>/tasks/` as it finishes, so a run that is
killed resumes where it stopped when started again.

`forecasts` is one grid or a list of grids of different kinds. In a grid,
`seed` may be a list, running the same forecast under each seed, and `scale`
sets the oracle's shrinkage (an IC-0 forecast needs one).

Kind `"factor"` runs `factor_forecast`, with keys named as its arguments:
`ic`, `n_factors` (default 3), `factor_share` (default 0.3),
`ic_persistence`, `ic_dispersion` (default 0), `quality` (`"spread"` or
`"vol"`), `quality_strength` (only when given) and `half_life`. Its loadings
come from the risk-history month's first horizon (so list the shortest
horizon first), and `"spread"` quality reads the evaluation month's quotes.

```json
"forecasts": {"kind": "factor", "ic": [0.02, 0.05], "factor_share": [0.0, 0.3],
              "half_life": 12, "quality": [null, "spread"], "seed": [0, 1, 2]}
```

Besides the report's own fields, every row carries the Sharpe ratio of the
P&L summed over each day (`sharpe_daily_mid`, `sharpe_daily_net`), the
honest unit for an intraday book, with a 95% interval from a bootstrap that
resamples whole days (`..._low`, `..._high`). The resampling is seeded and
depends only on the number of days, so intervals are reproducible and paired
across rows. A month has about twenty days: the intervals give the scale of
the uncertainty rather than exact coverage.

## Walk-forward

`walkforward.py` runs one spec, unchanged, on every consecutive (history,
evaluation) month pair whose caches exist, and asks what a single month cannot
answer: how far each configuration moves from month to month, whether the
rankings hold, and whether the answer depends on the market regime.

```bash
python -m experiments.walkforward experiments/specs/e4_harness_sensitivity.json \
    --months 2019-08..2020-12 --workers 4          # evaluation months; history is the month before
python -m experiments.walkforward SPEC --months 2019-08..2020-10 --seal-holdout   # while designing
python -m experiments.walkforward SPEC --months 2019-08..2020-12 --aggregate-only # re-summarize
```

Each pair is a per-month spec (`<name>_wf/<YYYY-MM>`, the evaluation month,
with `eval_month` and `history_month` substituted and `"save_daily": true`) run
in-process by `run.py`, so it resumes and reproduces like any run. A pair
whose months are not cached (`market1t-v2-YYYY-MM.npz` when the spec says
`"cache": "v2"`, else v1) is skipped and reported; nothing is downloaded.
`--pairs HISTORY:EVAL,...` names pairs explicitly (a non-causal pair is allowed
for smoke tests and marked). The aggregate describes the months of the last
invocation.

| Output under `results/<name>_wf/` | What it holds |
|---|---|
| `<YYYY-MM>/` | `run.py`'s files for that evaluation month, plus `daily.npz` |
| `rows.parquet` | every month's rows with `eval_month`, `history_month`, `segment`, `month_missing_days` |
| `daily.npz` | `(configurations, days)` gross, net and cost P&L summed per day, with `days`, `day_month`, `row_ids` |
| `configs.parquet` | per configuration: mean, spread, range and share of positive months of each metric; Sharpe pooled over every day with a paired day-block interval; pooled break-even EFQ; deflated Sharpe within its group |
| `stability.parquet` | per (forecast, horizon) group and over all rows, per segment: Kendall's W and its chi-square p, mean and worst Spearman between months, top-decile persistence, PBO with blocks of about a month |
| `regimes.parquet` | per day: realized volatility, quoted half-spread, cross-sectional dispersion (from the cache), and their day and month terciles |
| `regime_summary.parquet` | per configuration and tercile: Sharpe, mean daily P&L and break-even EFQ |
| `coverage.json` | per month: days missing against the NYSE calendar and the store index, thin days, early closes, the March 2020 halts |
| `summary.json`, `figures/wf_{months,trajectories,regimes}-{light,dark}.png` | the headline and the small multiples |

Months are tagged with the pre-declared protocol segments: `design`
(2019-08 to 2019-12, where the grid and the primary metric are frozen),
`stress` (2020-02 to 2020-04), `holdout` (2020-11, 2020-12) and `test`.
`"save_daily": true` works in any spec: `run.py` then also writes
`daily.npz` (per row, the P&L summed over each day), which the per-period
series cannot give back once saved.

## Prepared, not yet run: every month of the store

The 18-month extension is built and smoke-tested on one day, but has not been
run. It takes, in order:

```bash
python -m experiments.months                     # every month's v2 cache, raw deleted after each
python -m experiments.walkforward experiments/specs/<spec>.json --months 2019-08..2020-12
```

`months.py` downloads each month of the day store (about 1.5-1.7 GB, roughly
27 GB over the 16 months not yet local), writes its v2 cache (about 200 MB)
and deletes the raw month before the next, so peak disk stays at a few GB; the
compute is about 1-2 hours on one core. It is resumable after a restart. The
walk-forward then costs about one month's run of the spec per evaluation month.

## On a cluster

Everything above runs on a CPU: one month and all six specs take a few hours
on four cores. For the full 18 months, run `month_cache` over every month and
`walkforward.py` over each spec (above). Tasks are independent, so
`--workers` scales with cores.

The TFWM encoders (arXiv 2610.09048) need a GPU to embed a month. Embed with
TFWM's own script, then turn the panels into forecast files here:

```bash
# in a clone of github.com/fin-ai-lab/tfwm, on a GPU node
uv run scripts/eval/portfolio_ic_sharpe.py embed \
    --ckpt-dirs <released-encoder>/<eval-month> --panel-dir panels/

# here
uv run --extra experiments python -m experiments.tfwm_panels panels/*.npz
```

`tfwm_panels.py` fits the paper's ridge probe (alpha 10) on the panel's
training month against the demeaned raw return, writes
`results/tfwm/<panel>.npz`, and prints the probe's IC by horizon. A spec with
`"forecasts": {"kind": "file", "paths": [...]}` then scores those forecasts.
Set `"decision_spacing"` to the encoder's anchor spacing (2925 s at 8 anchors a
day); the harness reads the spacing from the decisions for `"rebalance":
"horizon"` itself. The run is restricted to the decisions the encoder was
evaluated at.
